# Media Curation & Routing (content-factory) — Design Spec

**Date:** 2026-07-05
**Status:** Approved (brainstorm)
**Scope:** Слой курации/маршрутизации сгенерированного медиа внутри папки проекта — новые MCP-инструменты content-factory (`gf_*`), форматы состояния, инварианты безопасности, контракт Hermes. Заземлено на реальном проекте `Q:\1brain\20_business\lion_films\projects\rusargo\ryaba`.

## Проблема

Hermes с трудом раскладывает сгенерированные результаты по папкам проекта, а 2026-07-04/05 при «сортировке» (перенос из временной папки в целевую внутри `media/`) **удалил множество генераций**. Причины:

1. **Нет владельца-инструмента** для курации генераций (черновик → кирпич → кадр → winner). Hermes делает это сырыми `mv`/`rm` — разрушительными по природе (затирание одноимённых, частичный сбой = потеря источника, нет проверки доставки).
2. Существующий безопасный маршрутизатор (`ingest_route`, плагин kf-стороны) — про другое: раскладка *входящих* файлов по крупным storage-корням; семантики «кирпич/итерация/winner» у него нет.
3. content-factory к Hermes ещё не подключён (Фаза 4 не выполнена) — Hermes генерит своим плагином `image_gen/google`, раскладывает вручную.

## Граница компетенций (решение)

| | knowledge-factory (kf) | content-factory (cf) |
|---|---|---|
| Владеет | индекс/поиск БЗ; грубая маршрутизация *входящих* файлов в storage-корни (`ingest_route`) | **всё сгенерированное медиа внутри проекта**: генерация + курация/раскладка/winner'ы |
| Семантика | «документ/референс/модель/секрет → такой-то корень» | «вариант набора / кирпич / итерация кадра / winner» |

Бренд-vault'ы `Q:/1brain/70_brands/<brand>/vault` (канон `STORAGE_ROUTING.md` §26/61/89) остаются **опциональным** кросс-проектным источником, который cf может читать. **Осознанное отступление от канона:** бренд-ассеты Рябы (лого, упаковка) остаются **внутри проекта** — принцип «один проект = одна папка» приоритетнее; миграция в vault — только если бренд реально расползётся на несколько проектов.

## Ядро модели

Два примитива, всё остальное — производные:

1. **Набор вариантов (variant set)** — именованная коллекция альтернатив/итераций одного и того же (`set_id = <kind>/<name>`). История набора **неизменяема**: файлы никогда не переименовываются/не двигаются/не перезаписываются.
2. **Winner** — один **подвижный** указатель «текущий лучший» на набор. Переназначается сколько угодно; пиксели всех вариантов в безопасности в истории → смена winner = перестановка указателя, потеря невозможна.

Производные: **кирпич** = набор, чей winner идёт на вход сборке кадра; **раскадровка** = winner'ы lineart-наборов; **контакт-лист** = монтаж winner'ов; **сборка кадра** (будущий `gf_assemble_shot`) = winner'ы кирпичей (lineart-композиция + cast-лицо + look-and-feel-свет/настроение + brand-продукт) → генерация → новый набор `final/shot-NN`.

### Рабочий процесс пользователя (наблюдён в Рябе)

Пер-кадрово: `lineart-vN` (композиция) → winner → photoreal/magnific итерации → winner финала. Когда готовы winner-лайнарты всех кадров — это раскадровка. Затем к лайнарту добавляются кирпичи (cast/look/brand) → мульти-референсная генерация финального кадра. Winner на ЛЮБОМ наборе (cast, локация, mockup — тоже) и может меняться до самого конца.

## Карта зон `media/`

```
<project>/media/
├── references/                  ← ВХОД проекта
│   ├── cast/<name>/                 варианты актёра/персонажа
│   ├── look-and-feel/<name>/        настроение/свет/стиль проекта
│   └── brand/<name>/                бренд-ассеты проекта (лого, упаковка) — для новых проектов
├── generated/<YYYY-MM-DD>/shot-NN/  ← НЕИЗМЕНЯЕМАЯ история генераций (+ prompts/*.json)
├── winners/<kind>/<name>.<ext>  ← ПРОЕКЦИЯ winner'ов (регенерируемая; для глаз/Obsidian/Telegram)
├── .gf_winners.json             ← ИСТИНА указателей
├── .gf_media_ledger.jsonl       ← append-only журнал операций
├── contact-sheets/<sheet_id>.png← стабильные имена; перегенерация заменяет
├── exports/                     ← деривативы (_tg/_show) и снапшоты «как отправили клиенту»
├── storyboards/                 ← рисованные раскадровки (вход)
└── _TO_PURGE/<date>/            ← мягкое удаление (hard-delete в системе нет)
```

**Виды наборов** (`kind`, расширяемо): `lineart`, `final` — история в `generated/<date>/shot-NN/` (варианты одного набора могут жить в разных датах — указатель хранит relpath, ему безразлично); `cast`, `look-and-feel`, `brand`, `location` (опц.) — история в `references/<kind>/<name>/`. Конвенции папок — дефолты для нового; манифест может указывать на любой файл внутри проекта (существующие структуры не ломаются).

**Мастера vs деривативы:** мастера — в истории; экспорты (`_tg.jpg`, `_show.jpg`) — в `exports/`, регенерируемы, их потеря безвредна. Существующие деривативы в Рябе не трогаем.

## MCP-инструменты (новые)

| Инструмент | Действие |
|---|---|
| `gf_add_variant(project, image_path, set_id, note="")` | **Копирует** файл (источник откуда угодно, read-only) в дом набора под **каноничным именем**; исходное имя+путь → в ledger. Источник не трогается. |
| `gf_set_winner(project, set_id, image_path)` | Правит `.gf_winners.json` (атомарно) + обновляет проекцию `winners/…`. Пиксели не двигаются. Переназначаемо. |
| `gf_list_sets(project, kind=None)` | Read-only инвентарь: наборы, число вариантов, текущий winner. |
| `gf_materialize_winners(project)` | Пересобрать `winners/` из манифеста + истории (проекция disposable). |
| `gf_contact_sheet(project, sheet_id, set_ids=[])` | Монтаж текущих winner'ов → `contact-sheets/<sheet_id>.png`; снапшот «как отправили» → копия в `exports/`. |
| `gf_discard(project, image_path)` | Мягкое удаление: copy→sha256→remove в `_TO_PURGE/<date>/`. Единственный способ «удалить». |
| `gf_adopt_set(project, set_id, dir)` | Регистрирует существующую папку как набор (скан → ledger `op:adopt`), без перемещений. Для принятия Рябы как есть. |

Прежний `gf_save_asset` из фазового плана Ф2 **заменён** парой `gf_add_variant`+`gf_set_winner`. Генеративный `gf_assemble_shot` — отдельная будущая фаза (входы: winner'ы кирпичей).

### Каноничные имена

- Референс-наборы: `<name>-NN.<ext>` (`kurtukova-07.jpg`); итерации кадров: `<stage>-vN.png` (`lineart-v3.png`).
- NN/vN — по union истории набора и ledger (не по одной папке).
- Проекция: `winners/<kind>/<name>.<ext>`; листы: `contact-sheets/<sheet_id>.png`.

## Форматы состояния

**`.gf_winners.json`** (истина; атомарная запись tmp+`os.replace`):

```json
{"version": 1, "winners": {
  "lineart/shot-02": {"path": "generated/2026-07-05/shot-02/lineart-v2.png",
                       "set_at": "2026-07-05T12:41:00Z",
                       "history": ["generated/2026-07-04/shot-02/lineart-v1.png"]}}}
```
`history` — только список relpath прошлых winner'ов (даты переназначений — в ledger).

**`.gf_media_ledger.jsonl`** (append-only, никогда не редактируется; паттерн `ingest_route`):

```json
{"ts":"...","op":"add_variant","set_id":"cast/kurtukova","path":"references/cast/kurtukova/kurtukova-07.jpg","original_name":"IMG_4211.jpg","source_path":"C:/.../IMG_4211.jpg","sha256":"...","note":"..."}
{"ts":"...","op":"set_winner","set_id":"lineart/shot-02","path":"...v2.png","prev":"...v1.png"}
{"ts":"...","op":"discard","path":"...","moved_to":"_TO_PURGE/2026-07-05/..."}
{"ts":"...","op":"adopt","set_id":"...","dir":"...","files":N}
```

Промпт-сайдкары cf-генераций: `generated/<date>/shot-NN/prompts/<имя>.json` (как в спеке генерации; в ledger не дублируются).

## Инварианты безопасности

1. История неизменяема; единственный выход — `gf_discard` (мягко).
2. Всякое перемещение = copy → sha256-verify → (только discard) remove. Хэш не сошёлся → копия удаляется, источник цел, ошибка.
3. Файлы истории никогда не перезаписываются (коллизия → авто-суффикс `_1`). Перезаписываемы только проекции (`winners/`, `contact-sheets/`).
4. Манифест — атомарная запись; битый JSON → ошибка с подсказкой восстановления из ledger.
5. Все целевые пути валидируются внутри `<project>/media/` (traversal-защита); `source_path` — только чтение.
6. Hard-delete в API отсутствует; `_TO_PURGE` чистит только человек.

**Ошибки** — структурированные (`{"error","hint"}`), не трейсы: несуществующий set_id, файл вне проекта, повисший winner (→ hint `gf_list_sets`) и т.п.

**Восстановление:** `winners/` → `gf_materialize_winners`; `.gf_winners.json` → replay ledger (последний `set_winner` на set_id); потеря ledger → пиксели и имена самодокументируемы (теряется только провенанс).

## Контракт Hermes

- Над медиа проектов Hermes использует **только** `gf_*`-инструменты; сырые `mv`/`rm`/перезапись запрещены гайдлайном (технически cf запретить не может — но safe-copy делает ошибку раскладки безвредной, а удаление канализировано в `gf_discard`).
- Цикл: `gf_list_sets` → `gf_add_variant` → показ пользователю → `gf_set_winner` **по слову пользователя** (выбор winner — решение человека; A+C из брейншторма) → `gf_contact_sheet`.

## Принятие Рябы (без ломки)

Ничего не переносим и не переименовываем. `gf_adopt_set` регистрирует существующие папки (`references/cast/kurtukova`, `generated/*/shot-NN`, …) как наборы. `-WINNER`-файлы: по указанию пользователя разово проставить `gf_set_winner` на оригиналы; суффиксы далее не нужны. Лого/упаковка остаются в `references/look-and-feel/{logo,packaging}` (см. отступление от канона).

## Фазировка

- **Ф2a — ядро курации:** модуль `gf/curate.py` (манифест, ledger, canonical naming) + инструменты `gf_add_variant`, `gf_set_winner`, `gf_list_sets`, `gf_materialize_winners`, `gf_discard`, `gf_adopt_set` + CLI-зеркала + тесты (tmp-проекты: хэш-фейл, коллизии, atomic, восстановление из ledger).
- **Ф2b:** `gf_contact_sheet` (PIL-монтаж; добавляет Pillow в зависимости).
- **Ф4 (приоритет повышен):** подключение cf к Hermes + гайдлайн «no raw mv/rm». Без этого потери продолжатся.
- Позже: `gf_assemble_shot` (мульти-кирпичная генерация финала; частично упирается в Nano/Gemini-блокер), интеграционный прогон на копии Рябы.

## Не-цели

- Автоматический выбор winner агентом (решает человек).
- Миграция существующих файлов Рябы / бренд-ассетов в vault.
- Маршрутизация генерации по бэкендам (подход B — отложен).
- Индексация медиа-содержимого (OCR/vision — домен kf, будущая веха).
